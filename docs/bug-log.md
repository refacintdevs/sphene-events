# EventIQ — Phase 0 Bug Log

This file documents bugs encountered during Phase 0 (Foundation) development. It is maintained as a dissertation appendix artifact, demonstrating systematic identification, diagnosis, and resolution of real defects encountered during the project.

| ID | Phase / Unit | Date | Bug Description | Root Cause | Fix Applied | Lesson Learned |

| BUG-001 | Phase 0, Unit 4 | 2026-05-25 | Initial seed script created only 2 vendor profiles instead of the spec'd 3 (the Decoration vendor "House of Lush" was missing), 4 services instead of 6, 0 portfolio items instead of the required 12, and the sample booking was in `PENDING_VENDOR` status instead of `PAID` with a corresponding `Payment` row. The database was technically populated but did not reflect the agreed seed state, which would have caused incorrect counts on the landing page and broken the booking flow demo. | The revised plan for Prisma 7 architecture changes — which introduced mid-flight clarifications about `prisma.config.ts`, adapter setup, and environment variable handling — did not carry forward the full seed data specification from the original plan. The AI assistant re-derived seed data from general context rather than from the explicit spec, producing a plausible but incomplete result. The root issue is context window fragmentation: prior decisions about seed data scrolled out of active context during a long multi-step plan. | The full seed specification was re-stated as a single self-contained block in a fresh instruction, listing every required record, field value, status, and date. The seed script was revised to use Prisma `upsert` (idempotent) rather than `create`, so re-running it is safe. After re-running, counts matched spec: 5 users, 3 vendor profiles, 6 services, 12 portfolio items, 1 booking (PAID), 1 payment (HELD). | Multi-step AI-assisted plans must consolidate all prior decisions into the active instruction, not assume that context established earlier in the session is still active. Long plans should be checkpointed with a single self-contained spec block before any data-population step. |
| BUG-002 | Phase 0, Unit 6 | 2026-05-26 | The `setUserRole` server action in `actions.ts` declared a TypeScript return type of `Promise<SetRoleError>`, implying the function always returns an error object. In practice, the function calls Next.js `redirect()` on success and therefore never returns normally on the happy path. The type contract was misleading: any caller reading the type signature would assume an error object is always returned and might incorrectly assume a missing return means failure. Although runtime behavior was correct, the type system was actively misleading. | Next.js `redirect()` works by throwing a special exception (`NEXT_REDIRECT`) that is caught by the framework rather than propagating to the caller. This means the function's return type can never actually be observed at runtime on the success path — the function exits via exception, not `return`. TypeScript cannot model "throws on success" in the return type without union-with-`never`, which was not applied. | Added a JSDoc comment above the function explaining that `redirect()` on success means the return type is only reached on error paths. The runtime behavior was not changed, as it was always correct; only the type contract documentation was clarified. A follow-up note was added to `code-standards.md` under the Server Actions section. | Server actions that call `redirect()` on success have an inherently non-obvious type signature. The pattern should be documented proactively in code standards so future actions are written with correct JSDoc from the start. Alternatively, use a discriminated union return type (`{ ok: true } \| SetRoleError`) and let the caller handle navigation explicitly — this is cleaner but more verbose. |
| BUG-003 | Phase 0, Unit 8 | 2026-05-28 | The sticky nav's mobile hamburger button rendered correctly and was visible at 375px width, but tapping it produced no visible response. The shadcn `Sheet` component that should have slid open to show the nav links never appeared. The button was interactive (focus styles applied), but the open/close toggle was non-functional, making the mobile nav completely inaccessible to users on small screens. | The `Sheet` was wired in controlled mode: the component received explicit `open={isOpen}` and `onOpenChange={setIsOpen}` props. With the installed combination of shadcn `Sheet` and the underlying Radix UI `Dialog` primitive at those versions, the `SheetTrigger` child's automatic toggle behavior was being suppressed when controlled mode was active and the initial state was `false`. The trigger fired `onOpenChange(true)` but the state update was not being batched correctly with the render cycle in the App Router streaming context. | Switched the `Sheet` to uncontrolled mode by removing the `open` and `onOpenChange` props entirely. Individual nav link items retained `SheetClose` wrappers so clicking a link still closes the sheet, which is the only programmatic control actually needed. The `isOpen` state variable was removed. Manual test at 375px confirmed the sheet opened and closed correctly after the fix. | Prefer uncontrolled mode for shadcn `Sheet` (and Radix Dialog primitives in general) unless there is a concrete requirement for programmatic control (e.g., closing the sheet from a parent component on route change). Controlled mode adds state management overhead and has version-specific edge cases with the App Router. |
| BUG-004 | Phase 0, Unit 8 | 2026-05-28 | The sticky nav had a `useEffect` scroll listener intended to switch the nav background from transparent to solid after scrolling past 10px. The nav rendered with a transparent background and never transitioned to solid, even after scrolling well past the threshold. This caused page content to visually bleed through the nav bar, making the header unreadable on pages with any content immediately below the fold. | Two compounding causes: (1) The `useEffect` registered the scroll event listener but did not call the handler immediately on mount, so `isScrolled` stayed `false` until the next scroll event. If the page loaded already scrolled (e.g., after a refresh or Clerk re-render mid-scroll), the initial state was always wrong. (2) When Clerk loaded and completed its auth state check, it triggered a React re-render of the `NavBar` component. The fresh component instance started with `isScrolled = false` and missed the scroll position that had already been established. Together, these meant the scroll state was lost on every auth-driven re-render. | The scroll handler was invoked once immediately inside the `useEffect` to set the initial state from the current scroll position. Additionally, `document.documentElement.scrollTop` was added as a fallback alongside `window.scrollY`, since Next.js App Router can route scroll state through the document element rather than the window in some configurations. Manual test confirmed correct behaviour after both a fresh load and a page refresh at a scrolled position. | Scroll listeners must call their handler once at mount time to capture the initial scroll position — registering the listener alone is not sufficient. Auth state changes in Clerk can trigger component re-mounts or re-renders that reset local state; components with scroll/position state must always initialize from the current DOM state rather than assuming `0`. |
| BUG-005 | Phase 0, Unit 4 (follow-up) + Vercel deployment | 2026-05-28 | The Vercel build pipeline failed during the `npm install` postinstall step (`prisma generate`) with the error: `PrismaConfigEnvError: Cannot resolve environment variable: DIRECT_URL`. This occurred even though `prisma generate` does not connect to a database — it only reads the schema to generate the TypeScript client. The build was not touching any database operation, yet it required a live database URL to be present. This blocked the first Vercel deployment entirely. | In Prisma 7, `prisma.config.ts` is a TypeScript module that is evaluated at import time when any Prisma CLI command runs, regardless of the subcommand. The file contained `env("DIRECT_URL")` to configure the migration datasource. Prisma 7 resolves all `env()` calls in `prisma.config.ts` eagerly at startup — before the CLI even determines whether the command needs a database connection. Every Prisma CLI invocation therefore requires all referenced environment variables to exist in the process environment, even for commands that never open a connection. Vercel's build environment had `DATABASE_URL` but not `DIRECT_URL`, which is intentional (DIRECT_URL is for migrations, not builds). | For local development: the postinstall script was updated to use `dotenv -e .env.local -- prisma generate` to load the variable from the local env file. For Vercel: `DIRECT_URL` was added to Vercel's build-environment variables (not the runtime environment) so it is available during `npm install`. The deployment succeeded on the first retry after this change. `env-variables.md` was updated to document that `DIRECT_URL` must be present in both local dev and Vercel build environments. | Prisma 7's configuration file uses eager environment variable evaluation. This is a breaking behavioral change from previous Prisma versions, where `datasource` blocks in `schema.prisma` were parsed lazily. Any project upgrading to Prisma 7 must audit all `env()` calls in `prisma.config.ts` and ensure those variables are available in every environment where any Prisma CLI command runs — including CI/CD pipelines and build systems. |
| BUG-006 | Phase 0, mid-development | 2026-05-25–26 | A file named `cls` (11 bytes, containing a pager dump of prior terminal output) appeared in the repository root and was accidentally committed in an early commit. The file had no purpose, cluttered the repo root, and added noise to the git history. It was not caught before commit because it resembled a short, lowercase file that could plausibly be part of a project. | While reviewing git log output inside Git's built-in pager (which uses the `less` pager and presents a `:` prompt at the bottom of the screen), the user typed `cls` intending to clear the PowerShell terminal. In the `less` pager, `:` followed by a filename writes the current pager output to that file — so `:cls` created a file named `cls` in the current working directory containing the pager's display buffer. The file was untracked and swept up in a subsequent `git add .` before the accidental artifact was noticed. | The `cls` file was deleted and the deletion was committed. To prevent recurrence, `git config --global core.pager "less -F -X"` was run: `-F` makes `less` exit immediately if the output fits on one screen (removing the pager prompt for short output), and `-X` disables terminal clearing on exit. With short git output no longer triggering the pager at all, the accidental `:filename` write pattern cannot recur. | Git's pager (`less`) has a different command vocabulary than the host shell. The `:` prompt is a `less` command interface, not a shell prompt — `q` exits, `:n` goes to the next file, and `:filename` writes to a file. Developers should configure Git's pager to auto-exit on short output (`less -F -X`) to avoid confusion, particularly on Windows where shell muscle memory for `cls` is strong. |
| BUG-007 | Phase 0, mid-development | 2026-05-25 | The `.env.example` file — which serves as a documented template for required environment variables and is intended to be committed to the repository as a developer onboarding artifact — was silently excluded from git tracking. `git status` showed it as untracked but `git add .env.example` had no effect; the file never appeared in `git diff --cached`. New developers cloning the repo had no template to understand what environment variables were needed. | The Next.js project scaffolder generates a `.gitignore` that includes the pattern `.env*` using a glob wildcard. This pattern matches `.env`, `.env.local`, `.env.development.local`, and so on — all of which should be ignored — but it also matches `.env.example`, which should not be ignored. Because the wildcard match takes precedence and there was no explicit allow-rule, `.env.example` was invisible to git. The issue was not immediately obvious because `git status` shows untracked-but-ignored files differently depending on `--ignored` flag usage. | The broad `.env*` wildcard in `.gitignore` was replaced with explicit per-file ignores: `.env`, `.env.local`, `.env.development`, `.env.production`, `.env.development.local`, `.env.production.local`, and `.env.test.local`. An explicit allow-rule `!.env.example` was added after the ignore block as a belt-and-suspenders measure. After the change, `git add .env.example` worked correctly and the file was committed. | Default `.gitignore` files generated by framework scaffolders should be treated as a starting point, not a finished configuration. Wildcard patterns like `.env*` are deliberately broad to protect against accidental secret commits, but they can suppress legitimate tracked files. Review and narrow any wildcard that could match files you intend to commit, and use `!` allow-rules for explicit exceptions. |
| BUG-008 | Phase 0, mid-development | 2026-05-25–26 | Git began producing CRLF-related warnings on virtually every file read or write operation on Windows: `warning: LF will be replaced by CRLF` or `warning: CRLF will be replaced by LF`. The working tree appeared constantly modified in `git status` even when no intentional changes had been made, producing false-positive diffs that obscured real changes. This made reviewing commits and confirming clean state unreliable. | PowerShell on Windows defaults to UTF-16 LE encoding with CRLF line endings for some file write operations. Git was configured with `core.autocrlf=true` (the Windows default), which converts LF → CRLF on checkout and CRLF → LF on commit. When files written by PowerShell (CRLF) were committed as LF and then checked out again as CRLF, the cycle was theoretically stable — but in practice, the mix of tools (Next.js dev server writing LF, PowerShell writing CRLF, Vercel expecting LF) created persistent churn. The Node.js toolchain and Vercel/Linux deployment target both expect LF exclusively. | Ran `git config core.autocrlf false` and `git config core.eol lf` to enforce LF line endings throughout the project, matching the Linux deployment target. A `.gitattributes` file was created with `* text=auto eol=lf` to normalize line endings for all text files at the repository level, independent of each developer's local git config. After running `git add --renormalize .`, all files were re-staged with consistent LF endings and the false-positive diffs disappeared. | Line endings should be standardized at the repository level via `.gitattributes` from the very first commit, not left to per-developer git config. On Windows, `core.autocrlf=true` is the git default but is wrong for projects that deploy to Linux. The correct project-level setting is `* text=auto eol=lf` in `.gitattributes`, which overrides local git config for any developer who clones the repo. |
